## Context

Review quality is bounded first by whether the intended code was actually analyzed. A PR reviewer evaluates committed base-to-head behavior, whereas worktree scope evaluates local uncommitted edits. Both are useful, but they are different facts and must never share an ambiguous green label.

## Goals and Non-Goals

### Goals

- Resolve an explicit immutable scope before analyzers run.
- Represent failure to resolve scope or mandatory tools as `UNKNOWN`.
- Compare base and head under identical analyzer identities.
- Distinguish introduced, fixed, unchanged, and unknown findings.
- Keep tests and analyzer-policy/configuration inputs visible in PR evidence by default.
- Separate severity, finding lifecycle, autofix availability, and policy.

### Non-Goals

- Invent more detectors or open-ended semantic judgments.
- Turn heuristics or AI hypotheses into deterministic blockers.
- Merge Requirements and review verdicts.
- Replace full tests, contracts, security, or human review.
- Authorize or prove semantic monotonicity of candidate analyzer-policy changes; C14 detects them and fails closed until a separate trusted promotion contract exists.
- Prove that intentionally adversarial candidate Python cannot falsify its own test/CrossHair process behavior or candidate-generated artifacts.

## Decisions

### Replace ambiguous changed scope with explicit sources

The CLI accepts:

- `--scope worktree`: tracked changes relative to HEAD plus untracked eligible files;
- `--scope index`: the exact staged/index blob snapshot relative to HEAD, materialized independently from later unstaged worktree edits;
- `--scope range --base-ref <full-ref> --head-ref <full-ref> [--pr-context-file <absolute-path>]`: committed merge-base-to-head delta; matching claimed context yields producer `range_candidate`, absence yields `range_preview`, and only a protected consumer verification envelope can yield effective `pr_range`;
- `--scope full`: all eligible repository files;
- positional files: one explicit caller-selected set labelled `scope_evidence.assurance_kind=explicit_files`; it is not pull-request range evidence.

`--scope changed` remains one-release deprecated compatibility for `worktree` and prints a warning. A PR assurance consumer requires a producer report with `scope_evidence.assurance_kind=range_candidate` plus a separate trusted verification envelope whose `effective_assurance_kind=pr_range`; it rejects range_preview, worktree, index, full, changed-alias, positional-file, or unenveloped candidate evidence. Explicit files remain valid for local/manual enforcement when no PR-range claim is made.

Range resolution runs the equivalent of `git merge-base --all` for the resolved full base/head commits and requires exactly one best merge-base commit. Zero results, multiple results from criss-cross history, duplicate/unparseable output, or object-resolution failure is `UNKNOWN`; CR14 defines no virtual-base synthesis. Range resolution always records the sorted candidate merge-base commit/tree identities plus canonical candidate-set digest and diagnostics. Only after uniqueness is proven does it record the analyzed merge-base commit/tree SHA; diff/path digest; selected file and line facts; rename/deletion facts; filters/facets; repository root; command request; resolver version; assurance kind; and diagnostics. Tests are included by default. Explicit facet exclusion is recorded and cannot be mistaken for analyzed evidence.

### Bind analysis to immutable commit content

`scope.py` is the only Git boundary. For index mode it SHALL atomically write the complete Git index tree once and materialize that captured tree outside the caller worktree. It SHALL derive governed staged paths, statuses, and rename/deletion facts exclusively from `HEAD` versus the captured tree object; it SHALL NOT enumerate selection from a later live-index read. Unchanged tracked dependencies/config/support retain their HEAD-plus-index bytes inside the same root. It records selected paths separately from the captured complete index tree and path/object-type/Git-mode/blob/content manifest, and analyzes/imports only from that root even when staged or supporting pathnames have additional unstaged edits. Concurrent index mutation after capture cannot change selection for that run; inability to diff or materialize the exact captured tree, or any captured-tree/object/selection mismatch, is `UNKNOWN` and requires a fresh resolution. Signed `tracked-regular-governed-input-v1` applies before applicability: every selected/eligible/invoked Python, test, test-support, policy, and configuration path must be a tracked `blob` with mode `100644` or `100755`; a staged symlink (`120000`), gitlink (`160000`), unmerged entry, intent-to-add entry without content, missing object, or other mode/type is governed UNKNOWN rather than silently excluded.

For range mode it SHALL materialize fresh, detached baseline and head roots outside the caller worktree. The baseline root is the resolved merge-base commit/tree; the supplied base-ref tip is recorded only as a resolver input and SHALL NOT be analyzed as the PR baseline. The head root is the resolved head commit/tree. For each snapshot, `scope.py` SHALL build a typed manifest for every selected analyzer input and every declared analyzer-configuration input. `AnalyzerInputIdentity` is the closed tagged union `git_blob | signed_module_payload | generated_projection | builtin_mode`. A `git_blob` binds repository, commit/tree, repository-relative path, tree-entry object type, exact Git mode, Git blob SHA, and content SHA-256. Under `tracked-regular-governed-input-v1`, only object type `blob` with mode `100644` or `100755` is valid for a selected/eligible/invoked Python, test, test-support, policy, or configuration input. `scope.py` traverses every materialized path component descriptor-relatively with no-follow/beneath semantics, rejects any symlink or non-directory parent, opens the final component no-follow, requires `fstat` regular-file identity, hashes that same descriptor, and proves equality with the committed Git blob and materialized-output digest. A recognized governed pathname whose tree entry is `120000`, `160000`, missing, or otherwise non-regular remains selected governed impact but yields `unsafe_governed_input` UNKNOWN before NOT_APPLICABLE or analyzer launch; dereferenced target bytes are never accepted. A `signed_module_payload` binds module name/version/checksum/signature, approved signing-key fingerprint, loader registration/origin, canonical installed-root and payload path, and content SHA-256 without inventing a reviewed-repository blob. For `module_code_payload`, `verified-installed-module-payload-v1` additionally binds the module loader's already-enabled root, exact deterministic full-payload verification algorithm/manifest/checksum/signature result, descriptor-relative copy manifest, and the available module name/version/checksum/signature package identity; source commit/tree is neither installed metadata nor required evidence, and the original registry archive is neither an input nor a requirement. A `generated_projection` binds generator ID/version/schema, parent input identity/digest, canonical logical transformation-map digest, root-token substitutions, and generated content SHA-256; its materialized absolute path is non-authoritative evidence only. A `builtin_mode` binds analyzer/tool version and exact mode/argv identity and has no file; it identifies behavior but never proves executable code. For `ai-bloat-ast` and `ast-clean-code`, it is valid only together with a `signed_module_payload` whose role is `module_code_payload`, whose identity satisfies `module-code-payload-v1`, and whose bytes are sealed inside the analyzer capsule. Every materialized file additionally binds its output SHA-256. Producer and protected consumer use the same canonical tagged representation and digest; `git_blob` is the only variant that may populate a reviewed-repository Git blob field. The runner receives only paths rooted in the appropriate materialization and runs the merge-base/head snapshots with the same pinned analyzer/toolchain and trusted policy/config digest.

The trusted policy/config selection is resolved once under a target-tip-first policy and applied to both range source snapshots. Governed target configuration wins when present. Only defaults explicitly named by this contract may come from the exact installed, signed Code Review module artifact; each fallback is materialized outside both source roots and the target-policy bundle, and binds module name/version/checksum/signature, canonical payload path, source blob/content digest, and selected-config digest. The protected PR/merge-queue workflow writes a canonical `github-actions-pr-v1` context file outside the checkout immediately before invocation, containing provider, repository, target ref, PR/queue, event, expected target-tip and head commit/tree identities and, when any import-capable profile member is applicable, the target-tip `project-runtime-layer-v1` descriptor and build attestation. The producer freezes a regular non-symlink context file, requires exact equality with resolved base/head identities, and binds its canonical digest, but treats the file as claimed provenance and emits only `range_candidate`; it cannot distinguish byte-identical local and protected-workflow files. Missing context produces `range_preview`; malformed, mismatched, moved, or unsafe context produces UNKNOWN. The protected consumer independently enumerates all best merge bases from workflow-native target/head identities, requires exactly one, and then recomputes that expected unique merge base and the complete governed merge-base-to-head diff; derives selected governed Python files/lines and governed policy paths/sections plus object-type/mode/status/rename/deletion facts and their canonical manifests/digests under the protected policy; resolves the authorized target-tip policy/config, declared project-runtime source-lock inputs and applicable builder/artifact attestation, and approved signed producer module/schema/profile/toolchain identities; and compares every value with the immutable producer report. It also verifies the report artifact's producer workflow/ref/run/attempt/job identity and artifact digest. It emits a separate verification envelope binding every compared identity, manifest, digest, and its own workflow/ref/run/attempt identity plus `effective_assurance_kind=pr_range`; rejection never mutates or upgrades the producer report. This consumer independently verifies selection and provenance, not analyzer semantics or findings. A mismatched, moved, untrusted, missing, or unreadable target identity or policy makes authoritative assurance UNKNOWN. `scope.py` materializes the target-tip policy bundle separately from both source roots and records its commit/tree plus every selected config path/blob/digest. The merge base remains the source-code comparison baseline; using current target policy does not turn target-only source commits into differential inputs. `runner.py` passes the sealed bundle through one invocation context; configurable adapters MUST NOT discover policy from either analyzed source root, the caller worktree, or process `.`.

This ownership boundary is deliberate: the module producer validates claimed context structurally, records complete candidate evidence, and publishes the signed schema/matrix contract. It does not implement a protected-workflow consumer or envelope emitter. The separate core adoption derives trusted event facts, recomputes governed selection/provenance, compares the immutable report, emits the envelope, and owns the corresponding runtime tests. Static accepted/rejected envelope examples in the module compatibility matrix are interoperability fixtures only and SHALL NOT be treated as workflow-native attestation.

### Use symmetric merge-base/head analysis

Range review evaluates the resolved merge-base snapshot and head snapshot with the same analyzer version, configuration digest, policy, and normalization. The current base-ref tip participates only in merge-base resolution; target-branch commits after divergence are never treated as the PR baseline or classified as feature-branch fixes. Signed `finding-multiset-v1` defines the complete identity and pairing algorithm. `identity_fingerprint` is SHA-256 over canonical JSON containing analyzer ID, rule/kind ID, rename-normalized repository-relative file path, the exact analyzer-emitted qualified symbol or null, and `normalized_message`. Message normalization is exactly Unicode NFC, CRLF/CR to LF, replacement of the validated active snapshot absolute-root token with `<SNAPSHOT>`, collapse of ASCII horizontal whitespace runs to one space, and trim; it never deletes digits, identifiers, quoted values, or arbitrary paths. Raw line/column/span and source context are excluded from identity and retained in `occurrence_evidence_digest`. Schema 1.6 gives every finding `location_kind=source_span|selector|non_source`. A source observation carries canonical `source-span-v1`: one-based inclusive start/end lines, zero-based UTF-8-byte start column and exclusive end column, `precision=exact|line`, plus the analyzer's raw coordinates/coordinate-system and conversion identity/digest. Adapters SHALL preserve and convert exact endpoints when their pinned output supplies them. When a source analyzer supplies only a valid one-based line, the controller deterministically sets a line fallback spanning byte columns `0..len(LF-normalized physical line excluding the terminator)` with `precision=line`; an invalid/missing path or line is invalid evidence, never guessed. Selector findings use exact selector identity/reconciliation and do not enter source occurrence pairing; infrastructure/non-source findings remain typed UNKNOWN facts. Every required or conditional profile member SHALL emit a canonical source span or its contract-named typed non-source location—never an untyped nullable line.

Source spans participate separately in signed `occurrence-continuity-v1`, because identity equality does not prove that two observations are the same occurrence. For each source observation the controller validates the canonical span against the immutable source blob and computes `continuity_anchor_digest` over canonical JSON containing: rename-normalized path; exact LF-normalized bytes of every physical source line intersecting the span; immediately preceding and following complete physical lines or explicit BOF/EOF sentinels; and start/end columns relative to the first/last spanned lines. No whitespace, comment, token, or path normalization is permitted in this anchor. An anchor is considered only when it resolves to exactly one distinct physical source location in base and exactly one in head. Signed `source-line-correspondence-v1` then compares the two complete LF-normalized physical-line sequences using insert/delete cost 1, replace cost 2, exact-line match cost 0, and no move operation. It records global minimum edit cost `G`, cost `F` with the exact contiguous anchor pairing forced, and cost `X` with that exact anchor pairing forbidden. Continuity is proven only when `F=G` and `X>G`; `F>G` is different; `F=G=X` or a non-unique anchor is ambiguous. The initial signed bound is at most 16 MiB and 20,000 physical lines per side and at most 4,000,000 dynamic-programming cells per evaluated file pair; exceeding a bound is unavailable. Algorithm/version, bounds, source-line sequence digests, anchor positions, `G/F/X`, and correspondence digest are evidence. Multiple identical analyzer emissions at one proven physical location remain a multiset and pair up to the minimum count. Within a proven-continuity group, occurrences partition by normalized severity plus derived blocking-input digest; identical partitions pair deterministically by occurrence digest and are unchanged, while residual continuous base/head observations are unknown severity/policy transitions. An identity-equal head observation with `continuity_status=different` is introduced. Missing or invalid span evidence, a non-unique/alternate-optimal anchor, or exceeded correspondence bounds produce `continuity_status=invalid|ambiguous|unavailable` and an unknown head transition, never unchanged or introduced; other unmatched head surplus is introduced, and every unmatched base occurrence is fixed subject to suppression and rename-fix overrides. The closed continuity status set is `proven|different|ambiguous|invalid|unavailable`. Bucket evidence binds base/head identity counts, canonical/raw span evidence, anchor bytes/digests and distinct-location counts, line-sequence/cost/correspondence evidence, continuity decisions, partition counts, pairing list, surplus lists, and canonical bucket digest. Thus an unrelated insertion before an otherwise byte-identical anchor may shift its reported line while remaining unchanged when forced correspondence is uniquely optimal; an identical block moved to a different edit location is introduced when forcing it raises global cost and is unknown when multiple optimal correspondences remain; a diagnostic deleted at one context and recreated at another is introduced; a second duplicate head emission at one continuous physical anchor is introduced; and context, duplicate, or mixed-severity ambiguity cannot collapse into PASS. Before fingerprint comparison, a head finding under the new side of a resolved one-to-one Git rename SHALL use that rename's old/base path as its canonical file anchor; the original head path and rename fact remain evidence. Copies and unpaired additions are not rename-normalized. All tools use this one source-blob/span/edit-correspondence contract; adapter-specific semantic, AST, symbol, fuzzy-context, move detection, or nearest-line matching is prohibited. Missing/invalid spans, ambiguous mappings, or unavailable bounds cannot support unchanged pairing or an introduced claim and remain unknown, and line-number/context equality alone is insufficient.

### Separate finding concepts

Finding fields distinguish:

- `severity`: impact if valid;
- `status`: open, fixed, or waived-by-reference;
- `differential_state`: introduced, fixed, unchanged, or unknown;
- `autofix_available`: whether a remediation mechanism exists;
- `blocking`: derived by the resolved policy.

An open fixable error remains unresolved and can block. Schema 1.6 reserves nullable `waiver_reference`, but C14 always emits it unset for newly derived findings and does not use it in blocking policy because no authenticated waiver ingestion/verifier exists. `governance-02-exception-management` owns future signed waiver behavior.

### Calibrate and version the terminal status

Schema `1.6` adds authoritative `assurance_status: PASS | FAIL | UNKNOWN | NOT_APPLICABLE` plus derived `has_unknown_required_evidence`. A report cannot say all validations passed when a mandatory scope/analyzer/claim is unknown or skipped. Mixed FAIL/UNKNOWN evidence uses aggregate FAIL because a validated blocker is sufficient to disprove acceptance; it retains the unknown flag/member evidence and never emits an all-complete summary. Facts, deterministic claims, heuristic signals, and optional AI hypotheses remain labelled separately; an unvalidated hypothesis cannot block.

For one compatibility release, `overall_verdict` remains a non-authoritative legacy projection: PASS maps to PASS or PASS_WITH_ADVISORY, FAIL maps to FAIL, UNKNOWN maps conservatively to FAIL, and NOT_APPLICABLE maps to PASS_WITH_ADVISORY plus explicit no-impact text. Non-shadow exits for those statuses are respectively 0, 1, 1, and 0; shadow always exits 0 while preserving the authoritative status.

Legacy `enforcement_mode` is the normalized policy request, not a scope label: `enforce` becomes `full`; `full`, `changed`, and `shadow` remain those values. `changed` is restricted to the one-release changed/worktree compatibility path. The parser represents an omitted enforcement option distinctly from an explicit value: omitted plus range normalizes to strict `full`, while omitted plus the deprecated changed/worktree path retains `changed`. Explicit range plus changed-mode is invalid; strict range writes `full`, shadow range writes `shadow`, and range identity lives only in `scope_evidence`.
