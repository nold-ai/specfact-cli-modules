# Change: Make Code Review Scope and Differential Enforcement Truthful

## Why

`specfact code review run --scope changed` currently means worktree changes from `git diff HEAD`, not the committed pull-request delta. On a clean PR checkout it can select no committed files. Git resolution failure becomes an empty changed-line map, allowing blocking findings to be treated as legacy and producing a green exit.

The report also lacks an honest unknown/not-applicable state, conflates autofix availability with resolution, and determines introduction primarily through changed-line intersection. These are evidence-boundary defects that must be fixed before adding more review rules.

## What Changes

- Define explicit scope sources: `worktree`, `index`, `range`, `full`, or positional files for explicitly labelled non-PR inspection. Keep `changed` only as a deprecated alias for `worktree`.
- Require full base/head refs for range scope, enumerate all best merge bases, proceed only when exactly one commit exists, derive the PR delta from that unique merge base, and reject any positional-file invocation that claims PR-range assurance. Zero or multiple best merge bases is `UNKNOWN`; CR14 does not invent a virtual-base algorithm.
- Materialize index analysis from the complete HEAD-plus-index tree and range analysis from the resolved merge-base/head commit trees in isolated roots, bind them with content manifests, and run every analyzer in a fail-closed OS filesystem sandbox rooted in a digest-pinned analyzer runtime capsule, exposing only its active read-only snapshot, exact read-only config inputs, sealed capsule rootfs, and process-private writable output/temp roots. Deny access to caller, opposite-snapshot, context, policy-source, and other-analyzer evidence roots; reject snapshot assurance when the required sandbox capability is unavailable. Also reject mutation-capable options for snapshot scopes and `focus=simplify` for range assurance because its finding filter is intentionally incomplete.
- Emit immutable scope evidence and fail closed as `UNKNOWN` when Git scope cannot be resolved. Treat the closed `governed-policy-paths-v1` analyzer/test/coverage-policy set—including the optional target `resources/semgrep-rules/ai-bloat.yaml` pack—as governed range impact alongside Python; a candidate policy diff is never NOT_APPLICABLE and remains UNKNOWN until a separately trusted policy-promotion contract exists.
- Reserve producer `assurance_kind=range_candidate` for a complete governed merge-base-to-head Python-and-policy selection with matching claimed context, and effective `pr_range` for a separate protected consumer verification envelope over that immutable report. This modules change implements and tests only the producer/report side plus the signed static consumer contract; workflow-native recomputation and envelope emission are owned and proved by the separate core adoption change. Changed tests are always included, and path/facet/test/execution-level narrowing options are rejected before analysis. A complete local range without context remains `range_preview`; partial review remains worktree or explicit-files.
- Analyze the resolved merge-base and head source trees with the same pinned analyzer/config identities and classify findings as introduced, fixed, unchanged, or unknown using stable fingerprints; normalize a head file anchor through the resolved one-to-one rename map before comparison, and never use the supplied base-ref tip as the source-code differential baseline. Bind the resolved base-ref tip to an authenticated expected target commit/tree that the consumer independently verifies, freeze that current target-tip policy bundle, and select only contract-named sealed defaults from the signed installed module when an adapter's governed target configuration is absent. Pass the resulting safe per-snapshot config projections explicitly to both source snapshots so candidate head configuration cannot suppress its own findings, relative paths cannot escape into policy/worktree content, consumer repositories do not need to vendor module defaults, and already-promoted target policy cannot be ignored. Candidate policy/config diffs are separately selected and digested as governed impact, but stay shadow-only and cannot authorize themselves. `pr-range-v1` does not attempt Python closure for analyzer extensions: non-empty Pylint `init-hook`, every non-empty alias of `extension-pkg-allow-list`/`extension-pkg-whitelist`, repository/unapproved Pylint `load-plugins`, and Coverage `[run] plugins` outside the signed profile manifest are unsupported UNKNOWN before applicability/launch. Any future accepted plugin must be an exact signed-toolchain profile member shared by both sides; the initial Pylint and Coverage plugin manifests are empty. Targeted pytest/coverage receives only explicit sealed target-tip policy projections—or their generated pinned defaults—with candidate auto-discovery and coverage environment overrides disabled. Every pinned-schema Coverage write destination is rewritten into the process-private output root; the read-only snapshot and configuration mounts are never Coverage data/report targets. Pytest policy selection follows the exact pinned pytest 9.0.3 locator across its complete supported source/section set. The pinned path schema classifies every path-bearing field/argv token as read/source or writable output: read paths are rebased onto the corresponding immutable snapshot, while `cache_dir`, `log_file`, `--basetemp`, `--junitxml`/`--junit-xml`, `--log-file`, and every other pinned writable destination are rewritten into deterministic process-private cache/temp/output paths. The controller passes both explicit `-c` and `--rootdir` and rejects unclassified, escaping, colliding, or ineffective writable-path projection. Coverage selection likewise includes every source recognized by pinned Coverage 7.15.4, including `.coveragerc.toml`, under its recorded precedence. Strict `coverage-exclusions-disabled-v1` explicitly clears Coverage's default exclusion/partial-branch regex sets and rejects any non-empty target `[report] exclude_lines`, `exclude_also`, `partial_branches`, or `partial_also` before launch; candidate text cannot exploit a target regex to inflate coverage. Before threshold evaluation, the normalized coverage file manifest must contain every governed production path present in the corresponding immutable snapshot exactly once; a target policy `source`/`include`/`omit` choice that leaves a governed path unmeasured yields `UNKNOWN`, never partial PASS. Every mandatory adapter SHALL satisfy signed `governed-input-completeness-v1`: bind each side's eligible/invoked input manifests, apply only pinned option-catalog transforms that prevent a governed file from being skipped or wholly silenced, and make catalog/effective-option/manifest mismatch UNKNOWN. The initial profile always passes Ruff `--no-cache` and `--no-force-exclude`; clears Pylint `ignore`, `ignore-patterns`, and `ignore-paths` in a bound generated projection; clears basedpyright `ignore` in each side projection; rejects every Semgrep rule-level `paths.include`/`paths.exclude` target-narrowing control before launch, then reconciles each accepted Semgrep pass's normalized JSON `paths.scanned` exactly against eligible inputs while retaining `paths.skipped`. Pass-level scanned union is not treated as per-rule proof; policy with rule-level narrowing is unsupported UNKNOWN. These controls preserve non-targeting analyzer rule semantics while preventing target policy from removing governed inputs; any newly accepted whole-file exclusion control requires a new signed profile and regression. Semgrep's optional AI-bloat pack is selected from the authorized target tip when present, otherwise from the exact signed module payload, and is sealed into the same explicit bundle for both snapshots; a candidate edit to that pack is governed UNKNOWN. Ruff configuration includes a sealed, manifest-bound target-tip transitive `extend` closure so an extended policy file cannot fall outside governed impact or sandbox inputs. Basedpyright likewise seals its target-tip `extends` graph and `baselineFile` artifact; absence of repository config produces the exact contract-named per-snapshot `basedpyright-default-v1` projection instead of implicit `--project .` discovery.
- Define the closed `pr-range-v1` analyzer profile and report its identity/coverage; incomplete required evidence is `UNKNOWN` when no validated blocker already proves FAIL. The released signed module SHALL provision the exact loader/analyzer versions bound by the profile and implementation checkpoint from its signed analyzer-environment lock—never ambient bare or lower-bound resolution—including explicit `pytest==9.0.3` and `coverage==7.15.4` lock entries. Analyzer-only direct or transitive distributions SHALL NOT be copied into `module-package.yaml:pip_dependencies`; that field remains the host/controller dependency contract and cannot safely carry the isolated analyzer closure. Portable Python distribution identity binds wheel or canonical `.dist-info/RECORD` payloads and normalized entry points, not environment-specific generated launcher bytes. A signed `pr-range-v1-toolchain-lock.json` closes the complete runtime dependency DAG for each initially supported Linux x86_64 CPython 3.11–3.13 environment and binds an immutable OCI base-rootfs manifest/layer digest. `toolchain.py` materializes an `analyzer-runtime-capsule-v1` rootfs from that base plus the exact/hash-checked analyzer lock, then seals the final interpreter, stdlib, extension modules, dynamic loader/shared libraries, analyzer payloads, bootstrap, and canonical root-manifest digest. Bubblewrap uses that capsule as its root filesystem with no host runtime mounts. Python analyzers start under the capsule interpreter with `-I -S` through the sealed bootstrap; snapshot roots are passed as validated data and inserted only after interpreter startup, never through startup `PYTHONPATH`, cwd path injection, site processing, or executable `.pth` files. The SpecFact core/module controller environment is outside the locked set, may contain unrelated core dependencies, and is never used as analyzer import or native-runtime resolution. Direct-only pins, ambient transitive resolution, or host-site leakage cannot activate the profile.
- Detect candidate-added inline analyzer/test/coverage suppression or analyzer-result control directives before finding fingerprint classification using the closed pinned `suppression-directives-v1` registry over Python comment tokens, including pinned Pylint `disable-all` and legacy `disable-msg=<rule-list>` spellings in addition to `disable`, `disable-next`, and `skip-file`; basedpyright `pyright: basic` and `pyright: standard` mode-lowering directives; and every source directive recognized by the pinned CrossHair parser, including special on/off forms and all `AnalysisOptionSet.directive_fields` assignments. An introduced, changed, or relocated directive is always an open blocking finding in CR14 and cannot make a baseline analyzer finding look fixed: diagnostic-suppression families emit `introduced_inline_suppression`, while basedpyright mode changes and CrossHair analyzer-result controls emit `introduced_analyzer_result_control`. CR14 accepts no suppression-waiver input; authenticated exceptions remain owned by the later `governance-02-exception-management` change. Parse/normalization uncertainty is `UNKNOWN`, and CR14 does not infer arbitrary suppression reach.
- Separate finding severity, lifecycle status, autofix availability, and blocking policy.
- Use `PASS`, `FAIL`, `UNKNOWN`, and `NOT_APPLICABLE` truthfully with closed aggregate precedence after differential/lifecycle classification: resolved no-impact is NOT_APPLICABLE; otherwise any valid completed blocker that remains open is FAIL; otherwise any required uncertainty is UNKNOWN; otherwise PASS. A baseline-only FAIL paired to a valid head PASS under identical policy remains per-snapshot evidence but is fixed/non-blocking and excluded from aggregate blockers. Mixed remaining FAIL/UNKNOWN retains every unknown member fact while aggregate remains FAIL. The schema reserves a nullable waiver reference, but CR14 has no waiver ingestion/verification path, always emits it unset for newly derived findings, and never changes blocking from it; signed exception behavior remains owned by `governance-02-exception-management`.
- Migrate the first-party review ledger to consume and persist schema 1.6 `assurance_status`; UNKNOWN and NOT_APPLICABLE are audit records but never passing streaks or reward events.
- Migrate every canonical merge/PR-quality instruction surface to protected-CI range/base/head/context/full usage; label a complete local range without authenticated event context `range_preview`, and retain worktree/positional commands only for local staged or simplification workflows that do not claim PR assurance.
- Publish a signed schema 1.6 consumer compatibility matrix covering all authoritative statuses, post-differential mixed FAIL/UNKNOWN precedence, legacy projections, exit behavior, accepted/rejected envelope fixtures, and the repository's exact schema-less `ledger update` input `{"run_id":"review-run-001","timestamp":"2026-03-16T00:00:00Z","score":85,"findings":[],"summary":"ok"}` plus its legacy normalization before any core consumer migration. The matrix is a static interoperability resource, not a module-side workflow verifier.

## Capabilities

### Modified Capabilities

- `review-run-command`: Resolve explicit snapshot scopes and perform deterministic base/head differential review.
- `review-finding-model`: Separate lifecycle, remediation availability, differential disposition, and policy.
- `review-cli-contracts`: Prove range selection, unknown handling, differential classifications, and analyzer coverage.

## Impact

- Planning artifacts only. No package source, tests, manifests, registry, version, signatures, prompts, or generated docs change in this commit.
- Later implementation changes the public review CLI and JSON schema additively, with a deprecation path for `--scope changed`.
- CI integrations that claim pull-request assurance must migrate to `--scope range --base-ref <base> --head-ref <head>` and require producer `scope_evidence.assurance_kind=range_candidate` plus a trusted envelope with `effective_assurance_kind=pr_range`; positional files remain valid only as `explicit_files` evidence and cannot satisfy that policy.
- Rollback: retain the legacy alias and dual-write old/new report fields during one compatibility release.

### Report compatibility and release gate

The additive authoritative field SHALL be `assurance_status` in `ReviewReport` schema `1.6`. For one compatibility release, producers SHALL also write the legacy `overall_verdict`, `ci_exit_code`, and `enforcement_mode` fields with this closed projection:

| `assurance_status` | Legacy `overall_verdict` | Non-shadow `ci_exit_code` | Shadow `ci_exit_code` |
|---|---|---:|---:|
| `PASS` | `PASS`, or `PASS_WITH_ADVISORY` when non-blocking findings remain | 0 | 0 |
| `FAIL` | `FAIL` | 1 | 0 |
| `UNKNOWN` | `FAIL` as the conservative legacy projection | 1 | 0 |
| `NOT_APPLICABLE` | `PASS_WITH_ADVISORY`, with an explicit no-governed-impact summary | 0 | 0 |

`enforcement_mode` is copied from the normalized enforcement-policy request, not from scope: `enforce` normalizes to legacy `full`; `full`, `changed`, and `shadow` serialize unchanged. `changed` remains valid for one release only with the deprecated changed/worktree path. Because the current CLI default is `changed`, an omitted enforcement option is resolved with scope awareness: range defaults to strict `full`, while the deprecated changed/worktree path retains `changed`. Explicit range plus `changed` is invalid; a non-shadow range run writes `full`, a shadow range run writes `shadow`, and `range` is never an `enforcement_mode` value. Scope truth remains in `scope_evidence.requested_scope`, `effective_scope`, and `assurance_kind`.

The new field is authoritative; dual-writing MUST NOT rewrite `UNKNOWN` or `NOT_APPLICABLE` to `PASS`. The modules repository's own staged `scripts/pre_commit_code_review.py` consumer SHALL use schema `1.6` `assurance_status` and `ci_exit_code` as authoritative, so changed-line fallback cannot turn UNKNOWN into exit zero; only reports older than `1.6` retain the existing staged-line compatibility calculation. Schema 1.6 first-party consumers, including `code review ledger update`, SHALL read `assurance_status` rather than the legacy projection. The ledger persists UNKNOWN and NOT_APPLICABLE explicitly, retains the complete canonical schema 1.6 report as `report_json` plus `report_digest` in local and Supabase run records, applies zero reward, and leaves both pass and block streak counters unchanged. Reports older than 1.6 retain their prior PASS/PASS_WITH_ADVISORY/FAIL ledger behavior. The exact schema-less ledger fixture normalizes under the existing legacy reader to `schema_version=1.0`, `reward_delta=5`, `overall_verdict=PASS`, and `ci_exit_code=0` from its score 85 and empty findings, while preserving run/timestamp/score/findings/summary; it does not gain authoritative `assurance_status`. Any schema older than `1.6` may be read only as legacy `PASS` (from `PASS` or `PASS_WITH_ADVISORY`) or `FAIL`; it can never be upgraded by inference to `UNKNOWN` or `NOT_APPLICABLE`. Schema `1.6+` with a missing or invalid `assurance_status` is invalid/unknown and cannot pass.

The first signed C14 module release SHALL set `core_compatibility: '>=0.56.0,<1.0.0'` only after a pre-release runtime smoke uses an immutable minimum supported core `0.56.0` tag plus recorded full commit/tree identity in a fresh environment, installs the candidate module package, loads it through that core, and validates the complete schema `1.6` consumer matrix. If that immutable core identity is unavailable or any install/load/matrix case fails, release and compatibility metadata remain blocked. This minimum-version smoke proves only advertised load/schema interoperability; actual protected core PR-CI migration is explicitly downstream of the signed release. The behavior-ready implementation PR regenerates command references and public docs; the canonical post-merge publish workflow alone generates and signs registry/archive/checksum/sidecar artifacts. A separate accepted core adoption change then pins those final signed identities, authors and proves the workflow-native consumer tests, implements the protected consumer/envelope emitter, and requires the verified `pr_range` envelope; it never adopts a feature-branch package. Module completion SHALL NOT claim those downstream runtime tests as module evidence.

## Explicit Non-Goals

- Add or change individual Ruff, Radon, Semgrep, basedpyright, pylint, contract, or AI-bloat detectors.
- Fuse Requirements verdicts into Code Review.
- Perform LLM review or claim semantic completeness.
- Infer historical pytest dependency closure.
- Implement analyzer-policy promotion or semantic monotonicity comparison; C14 detects the closed candidate policy/config diff and reports UNKNOWN, while a separate accepted trust-epoch/policy-promotion contract is required to authorize it.
- Implement the global governance evidence graph.
- Claim hostile-candidate resistance for pytest, CrossHair, or any analyzer that executes candidate Python. CR14 isolates other evidence roots but does not make candidate-authored runtime output an independent security attestation.
